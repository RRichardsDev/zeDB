# zeDB

A fast, native database exploration and fleet migration tool. Rust, GPUI,
ClickHouse first.

## One-liner

Zed-grade responsiveness for exploring databases, combined with a
git-backed migration engine that can manage schema state across hundreds of
databases on multiple clusters, showing exactly which migrations have been
applied where.

## Why it should exist

- ClickHouse tooling is weak. DBeaver's support is shallow, Tabix is dated,
  DataGrip is generic. Nothing offers fleet-wide migration state at all.
- Existing migration tools (Flyway, Liquibase, Atlas, dbmate) interpret SQL
  text or demand a declarative re-description of the schema. The proven
  alternative (from analytics-clickhouse-ddl, this project's ancestor):
  migrations are plain SQL, and the tool derives consequences by replaying
  them through a real, version-pinned `clickhouse local`. The database is
  the parser; the tool never becomes a second, drifting ClickHouse.
- Native GPU-accelerated UI makes the painful parts of DB GUIs (scrolling
  huge result sets, browsing thousands of objects) instant.

## Audience

Open source, for the ClickHouse community, built in the open. Opinionated
about migration layout and workflow; those opinions are the product.

## Design principles

1. **Replay, don't interpret.** Semantic questions about SQL are answered by
   a real pinned ClickHouse, never by reimplementing its semantics.
2. **ClickHouse is first-class; other engines are guests.** The driver
   abstraction is capability-based: a driver declares what it supports
   (explore, migrate, regen, verify). zeDB works as a fast explorer for
   other databases, but the migration engine is only promised where the
   engine's tooling makes replay possible. No lowest-common-denominator
   design.
3. **Headless core.** All logic lives in a core crate. The CLI and the GPUI
   app are both thin clients of it. CI never needs the GUI.
4. **Production is a loaded gun.** Mutating a live fleet requires explicit,
   layered consent: environment tiers with distinct visual identity,
   read-only-by-default connections, mandatory rendered dry-run diff before
   apply, rollback-class acknowledgement, and a local audit log. Safety is
   architecture, not a dialog box.
5. **BYO git.** Migration repos are plain directories under any git remote.
   No forge coupling, no GitHub assumptions.
6. **Provision from current state, upgrade through the chain.** New
   databases are provisioned from generated `current-state/`; existing ones
   walk the ordered migration chain. Humans write migrations only;
   current-state is generated and committed.

## Architecture

```
zedb/
  crates/
    zedb-core/      # domain model: repos, migrations, fleet, state, diffing
    zedb-driver/    # driver trait + capability model
    zedb-ch/        # ClickHouse driver: HTTP client, clickhouse-local replay,
                    # canonicalization, version pinning
    zedb-cli/       # thin CLI over core (CI entry point: regen, check, status,
                    # upgrade, verify)
    zedb-app/       # GPUI application
```

- **Driver capabilities** (initial set): `explore` (introspect + query),
  `migrate` (apply chain, track state), `regen` (derive current-state via
  replay), `verify` (diff live schema against expectation). The ClickHouse
  driver implements all; a future guest driver may implement only `explore`.
- **ClickHouse connectivity:** HTTP interface with a hand-rolled
  `RowBinaryWithNamesAndTypes` decoder into a dynamic value model. (The
  `clickhouse` crate was rejected: it is built around compile-time serde
  row structs, while an explorer discovers column types at runtime.)
  Native protocol is not a v1 concern.
- **Replay engine:** manages a cache of pinned `clickhouse local` binaries.
  Multiple clusters may run different server versions, so the pin is
  per-repo (checks) and per-cluster (verify), not global. The version is
  discovered from the connected server (`SELECT version()`), and the
  matching binary is downloaded on demand into the cache the first time
  that version is needed; nothing is preinstalled or hardcoded. Regen and
  verify always replay against the same version as the target server, so
  "the checks pass" always means "against the server we actually run".
- **Editor/grid:** built on GPUI primitives; tree-sitter for SQL
  highlighting. Expect to build the virtualized data grid and editor widget
  ourselves; upstream reusable findings to GPUI where possible.

## Migration model

A cleaned-up second generation of the analytics-clickhouse-ddl format.
Carried over because they are proven:

- Append-only, globally ordered migration chain of plain SQL
  (`upgrade.sql` + `rollback.sql`), no annotations, no redeclarations.
- Generated `current-state/` tree, never hand-edited, verified in CI
  (`regen --check`), regenerated by replaying the chain through the pinned
  local server. Data-only statements cause zero churn.
- Rollback classes declared on line 1 (`clean` / `structural` /
  `irreversible`) and enforced at check time and run time.
- Targeted (opt-in) migrations with a marker file, applied per database,
  ignored by fleet operations, graduable into the chain.
- `stamp` to adopt existing schemas; `verify` to detect drift.
- Identifier-position templating (`${db}`, `${cluster}`, ...) with strict
  validation, rendered per target.

Deliberately reconsidered for the new format (design during Phase 1, not
inherited blindly):

- Directory layout and numbering scheme (the `YYYY/MM/NNNNN` + increments
  of 100 shape is a candidate, not a given).
- Tracking table name/schema (`default.schema_migrations` is the ancestor;
  the new format may version its tracking schema explicitly).
- Template parameter set: the ancestor's analytics-specific offsets
  (`${refresh_offset}` etc.) become user-defined per-repo parameters, not
  built-ins.
- **Importer:** a one-time `zedb import` converts an
  analytics-clickhouse-ddl repo (layout, tracking rows, templating) into
  the new format. This is the bridge to testing against the real fleet.

## Fleet model

- A **connection** points at a logical cluster (or single node), contains
  one or more node or load balancer endpoints for connectivity and failover,
  and has shared credentials plus an environment tier (dev / staging /
  production).
- Databases are **discovered live** from the servers (system tables and,
  where present, an application-level registry query configured per repo).
  The fleet is not a checked-in inventory file.
- Exclusion groups (the ancestor's `exceptions.toml`) are repo-level config
  for deliberate targeting.
- The **fleet view** is the flagship screen: databases x migrations matrix,
  showing applied / pending / customised / drifted per database, filterable
  at hundreds-of-databases scale.

Cluster management scope is schema and migration state only. Live ops
(replication lag, mutation queues, query monitoring) stay in existing
observability tooling. See IDEAS.md.

## v1 scope

Phased; each phase is usable on its own.

**Phase 0: the explorer.**
- Connect to ClickHouse (multiple saved connections, environment tiers,
  read-only by default).
- Schema tree (databases, tables, views, MVs) with DDL view.
- Query editor with tree-sitter SQL highlighting and optional full Vim mode.
- Virtualized results grid that stays responsive on millions of rows.

**Phase 1: the migration engine (headless).**
- New repo format finalized; `zedb-core` + `zedb-cli` implement scaffold,
  regen, checks (sql / equivalence / lifecycle), status, upgrade, rollback,
  stamp, verify.
- Pinned-binary management.
- Importer from analytics-clickhouse-ddl.

**Phase 2: the fleet view.**
- Read-only first: status matrix, drift indicators, rendered dry-run diffs.
- Then applies from the GUI, behind the full safety ladder.

**Follow-ups (explicitly not v1):** zeDB writing to git itself (commit
scaffolded migrations, push); until then it reads the repo and the user
commits through their normal workflow. Everything else parked in IDEAS.md.

## Non-goals

- Being a generic multi-database migration tool. Guest drivers get
  exploration, not promises.
- Live operations console (kill query, user management, replica actions).
- Forge integration (PRs, reviews). BYO git means git, not GitHub.
- Windows for v1. macOS first, Linux close behind (GPUI maturity and no
  native Windows ClickHouse binary both point the same way).

## Risks

- **GPUI is raw.** Sparse docs, API churn, no widget library. Budget real
  time for UI infrastructure; treat upstreamable findings as a side goal.
- **Scope.** This is three products (explorer, migration engine, fleet
  console). The phase gates above are the defense; finish phases, resist
  blending them.
- **Replay depends on binary availability.** `clickhouse local` per version
  per platform must be fetched, cached, and pinned; failure modes (no
  binary for a version/platform) need graceful degradation to text-only
  checks.
- **A GUI that mutates fleets.** The safety ladder (principle 4) must exist
  before the first mutating action ships, not after.

## Open decisions

- Exact new repo format (layout, numbering, tracking schema, config file
  format and name).
- Result streaming format (RowBinary vs Arrow) and grid memory model for
  very large result sets.
- Name/branding: "zeDB" working title.
- License (leaning permissive or source-available; decide before publishing).
